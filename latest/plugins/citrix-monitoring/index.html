    Citrix monitoring plugin¶

    Article last updated: 2026-10-26.

    What it does¶

    The Citrix monitoring plugin collects the state of a Citrix server through the Pandora FMS Windows agent and prints it as Pandora FMS modules. Each run reads four groups of data from the server it runs on:

    • Performance counters. Every counter path listed in the counters file, sampled with Get-Counter.
    • Service state. For every Windows service display name listed in the services file, 1 while the service runs and 0 otherwise, queried through WMI.
    • Sessions. The number of active sessions the server currently reports.
    • Connected users. The number of logged-on user sessions the server currently reports.

    The plugin runs as an agent plugin: the Pandora FMS Windows agent executes it at every agent interval and ingests the <module> blocks it writes to standard output. It has no server plugin mode, sends nothing over the network and delivers nothing through Tentacle: everything it reports comes from the server where the agent runs. The usual arrangement is therefore one agent per Citrix server, with the plugin installed next to that agent.

    All of its configuration is a command line plus two plain-text lists. The plugin reads no other configuration file, keeps no state between runs and creates no agents of its own.

    Citrix NetScaler is a different addon and is not covered by this page.

    Requirements¶

    1. A Windows Server host with the Citrix role or components you want to monitor. The counters and services in the shipped lists belong to Citrix Presentation Server / XenApp 6 and to Windows itself. A host without those components simply has no such counters: the plugin reports the Windows counters and the services whose display names match.
    2. Windows PowerShell and WMI enabled. The plugin is a PowerShell script and reads service state through WMI.
    3. grep, gawk and wc available in the PATH of the account that runs the plugin, on the monitored server. The shipped implementation uses them to extract the service state and to count sessions, and it has no fallback when they are missing.
    4. The Pandora FMS Windows agent, installed on the same Citrix server and configured to run agent plugins.
    5. A PowerShell execution policy that allows the script, as described in Permissions and execution policy.

    No database, no API endpoint and no remote credential is involved: the plugin reads the local server.

    Install the plugin¶

    Download the package from the Marketplace entry, whose download is limited to licensed users, and copy its files to the Citrix server:

    • The plugin script, Pandora_Plugin_Citrix.ps1.
    • The counter list, counters.txt.
    • The service list, services.txt.

    Place them in any folder the agent account can read, normally the util folder of the agent installation, and keep the two lists together with the script: throughout this page <PATH_TO_CONFIG> is that folder.

    The lists are ordinary text files that you edit. They are not generated by the plugin and the plugin never writes to them.

    Configure¶

    The plugin has no console screen and no configuration file of its own. To put it to work you add one module_plugin line to the agent configuration and write the two lists.

    Run the plugin from the agent¶

    Add the plugin to the pandora_agent.conf of the agent installed on the Citrix server. One line is enough:

    module_plugin "C:\Windows\System32\WindowsPowerShell\v1.0\powershell.exe" -ExecutionPolicy Bypass -File <PATH_TO_CONFIG>\Pandora_Plugin_Citrix.ps1 -perf <PATH_TO_CONFIG>\counters.txt -serv <PATH_TO_CONFIG>\services.txt 2> <PATH_TO_CONFIG>\plugin_error.log
    • -File must be followed by the absolute path of the plugin script.
    • -perf receives the path of the counter list; -serv receives the path of the service list.
    • -ExecutionPolicy Bypass allows this process to run the script whatever the machine policy is. Remove it when the machine policy already allows the script; it has no effect when a Group Policy sets the execution policy.
    • 2> <PATH_TO_CONFIG>\plugin_error.log writes the diagnostics of the run to a file, because the agent only reads standard output. Without it, PowerShell's error output is lost.

    Restart or reload the agent after editing the file. The agent executes the plugin at every agent interval and ingests its output as the modules of the agent itself.

    The options of the plugin are independent, so the same line covers the supported combinations:

    Command line Modules generated
    No parameters, or -perf perfcounters The usage summary only; no modules
    -perf <PATH> Counters as generic_data, services, sessions and users
    -perf <PATH> -inc <any value except incremental> Counters as generic_data_inc and generic_data, services, sessions and users
    -perf none Services, sessions and users; no counter modules
    -serv none Counters, sessions and users; no service modules
    -perf none -serv none Sessions and users only

    -perf defaults to perfcounters, which is the value that prints the usage summary. That default is why the pure default invocation produces no modules: always pass the counter list, or none, explicitly.

    Write the counter list¶

    The counter list is one performance counter path per line, in the \Object(Instance)\Counter syntax that Get-Counter accepts. A line that names a multi-instance object without an instance, or an object that the host does not have, cannot be sampled: check every line on the target server.

    The shipped list monitors processor, memory, paging file and disk throughput, plus Citrix Presentation Server, Citrix Licensing and the IMA service. See Counter list for its exact content.

    Two properties of the file matter in practice:

    • Trailing spaces. The shipped file ends most lines with a space. The path is passed as it is read, so remove the trailing space when a counter is not collected.
    • Localized counter names. Counter names follow the operating system language. On a non-English Windows the shipped paths do not resolve; list the local names instead.

    To obtain the counters a server actually provides:

    Get-Counter -ListSet * | Select-Object -ExpandProperty Paths > counters.txt

    That file is a starting point: delete the counters you do not need and keep one per line.

    Write the service list¶

    The service list is one Windows service display name per line, as shown in the Name column of the services console — not the short service name. The plugin builds a WMI query with the line verbatim, so the value must match exactly, with no trailing space and with the capitalization of the display name.

    A line that matches no service still produces a module, with value 0, so a typo looks like a stopped service. See Service list for the shipped entries and their known quirks.

    Permissions and execution policy¶

    • The agent account must be able to read the plugin script and the two list files, and to execute powershell.exe.
    • The PowerShell execution policy of the account must allow the script. This is normally solved by signing the script, by setting a policy that allows local scripts, or by passing -ExecutionPolicy Bypass in the invocation shown above.
    • No official source for this addon documents a required role or a narrower permission set. Grant the agent account only what the plugin uses: read the script and the two lists, execute powershell.exe, and read the local performance counters and the local WMI service data.
    • The plugin produces diagnostics on standard error, and those messages can include the path of the script and of the lists: keep the error log readable only by the agent account.

    counters.txt and services.txt are plain text and can be deployed like any other agent file, for example with a file collection or a policy, so the same lists reach every Citrix server without editing them one by one there.

    Verify¶

    Run the plugin manually on the Citrix server, from a PowerShell window, before you rely on the agent:

    powershell.exe -ExecutionPolicy Bypass -File <PATH_TO_CONFIG>\Pandora_Plugin_Citrix.ps1 -perf <PATH_TO_CONFIG>\counters.txt -serv <PATH_TO_CONFIG>\services.txt

    A successful run prints one <module> block per generated module on standard output and ends. The excerpt below shows the last two blocks, the pair the plugin always generates:

    <module>
<name><![CDATA[Citrix Sessions]]></name>
<type><![CDATA[generic_data]]></type>
<description><![CDATA[Opened active sessions on server]]></description>
<data><![CDATA[3]]></data>
</module>
<module>
<name><![CDATA[Users_Connected]]></name>
<type><![CDATA[generic_data]]></type>
<description><![CDATA[Users connected to this server]]></description>
<data><![CDATA[3]]></data>
</module>

    Citrix Sessions and Users_Connected are generated by every run that generates modules, so if they do not appear nothing else was generated either.

    To read the usage summary, run the script with no parameters at all:

    powershell.exe -ExecutionPolicy Bypass -File <PATH_TO_CONFIG>\Pandora_Plugin_Citrix.ps1

    The plugin has no help option: -h is not a parameter of the script and only produces a PowerShell parameter error. The summary is the default behaviour of the script, because -perf starts at perfcounters.

    In Pandora FMS, open the agent that runs the plugin and confirm that the module list of its last contact contains Citrix Sessions, Users_Connected, the Status of service ... modules and the PerfCounter ... modules.

    Understand the results¶

    The plugin generates the same module catalog on every run. The four groups answer different questions and fail independently:

    • Counters. One generic_data module per counter sample, named PerfCounter <counter path>. The path is the one the host returns, so the module name contains the object, the instance and — for many counters — the server name. Two servers never share these module names.
    • Services. One generic_proc module per line of the service list, named Status of service <display name>, with 1 when the extracted state is exactly Running and 0 in every other case, including a service that does not exist.
    • Sessions. Citrix Sessions, a generic_data module with the number of lines of query session that contain Active.
    • Users. Users_Connected, a generic_data module with the number of lines of quser that contain Active.

    Neither count deduplicates accounts: both count active session lines, from two different Windows commands, so a user with two open sessions counts twice. When one command is unavailable, the corresponding module is the only indication.

    The counter group and the service group are independent, and so are they from the session pair: a counter file that cannot be read leaves the counter group empty, a service file that cannot be read leaves the service group empty, and the session modules are still generated.

    When a counter list is supplied, generic_data is the default module type. The generic_data_inc type is added only when -inc receives a value other than incremental, and it is added in addition to the absolute modules, not instead of them: both sets are named PerfCounter <counter path> and read the same file.

    Operate and troubleshoot¶

    • Every run is independent: the plugin samples the server, prints the modules and exits. There is no cache, no state and no service to restart.
    • The plugin has no interval of its own. The agent interval of the module_plugin line decides how often it runs.
    • There is no verbose or debug flag. The diagnostic channel is standard error, which the example invocation redirects to plugin_error.log.
    • The plugin resizes the console buffer at start-up, so it expects a console host. If a run started by the agent produces nothing while the same command works in an interactive PowerShell window, that difference is the first thing to check.
    Symptom Cause and fix
    The output is the usage summary instead of modules -perf was left at its default perfcounters, or -perf perfcounters was passed. Pass the counter list path, or none.
    A parameter cannot be found that matches parameter name 'h' The plugin has no -h. Run it with no parameters to print the summary.
    No PerfCounter module at all The counters file could not be read, or Get-Counter rejected every path. Check the path of the file and then the counter paths of Counter list on that server.
    Some counters are missing Those paths do not exist on that host, name a localized counter, or need an instance such as (_Total). Compare with the output of Get-Counter -ListSet *.
    A counter is not collected and its line ends with a space The path is passed exactly as written. Remove the trailing space.
    Every service reports 0 The display names do not match, or grep/gawk are not in the PATH. Compare a line of the list with the display name shown by the services console and check that both tools resolve.
    Get-Content : Cannot find path ...\services -serv was not passed, so the default value services was read as a file name. Pass the service list, or -serv none to skip that group.
    You cannot call a method on a null-valued expression and the run stops wc is missing, so the session counter has no value to trim. Add wc to the PATH.
    grep or gawk is not recognized The tool is not available to the agent account. Install it or add its folder to the PATH of that account.
    The agent creates no modules although the manual run prints them Check the -File path, the execution policy of the agent account, and the error log written by 2>.
    ... cannot be loaded because running scripts is disabled on this system The execution policy blocks the script. See Permissions and execution policy.
    Module names are not the ones in the list Counter modules are named after the path the host returns, which includes the object, the instance and the server name. That is expected.

    The plugin does not set an exit status of its own and does not stop on the errors it produces: a run that cannot read a list file reports the error on standard error and finishes, so the agent does not detect the failure. Read plugin_error.log when a module stops updating.

    Invocation parameters¶

    Option Required Default Description
    -perf No perfcounters Path of the counter list. Any value other than perfcounters and none is read as a file. none skips the counter group. The default value perfcounters only prints the usage summary.
    -serv No services Path of the service list. Any value other than none is read as a file. none skips the service group. The default value services is a bare word, not a path, so pass the file explicitly.
    -inc No incremental Mode selector, not a path. With the default value incremental the counter modules are generic_data. With any other value the plugin also emits one generic_data_inc module per counter, read from the -perf file, while the generic_data modules are still emitted.

    The options are PowerShell parameters: they are case-insensitive, each one takes exactly one value, and a name the script does not define is rejected before the run starts. The script defines no -h, -help or -verbose.

    Execution modes¶

    Command line Counter modules Service modules Citrix Sessions and Users_Connected
    No parameters None (usage summary only) None None
    -perf perfcounters None (usage summary only) None None
    -perf <PATH> generic_data From -serv Yes
    -perf <PATH> -inc <value other than incremental> generic_data_inc and generic_data From -serv Yes
    -perf none None From -serv Yes
    -perf <PATH> -serv none generic_data None Yes
    -perf none -serv none None None Yes

    Citrix Sessions and Users_Connected are generated by every run that gets past the usage summary, whatever the counter and service options are.

\PhysicalDisk(_Total)\% Free Space

\LogicalDisk(_Total)\Current Disk Queue Length
\LogicalDisk(_Total)\ Avg. Disk Sec/Read
\LogicalDisk(_Total)\ Avg. Disk Sec/Write
\LogicalDisk(_Total)\ Avg. Disk Sec/Transfer
\PhysicalDisk(_Total)\ Avg. Disk Sec/Read
\PhysicalDisk(_Total)\ Avg. Disk Sec/Write
\PhysicalDisk(_Total)\ Avg. Disk Sec/Transfer
\Citrix MetaFrame Presentation Server\Application Resolution Time (ms)
\Citrix MetaFrame Presentation Server\DataStore Connection Failure
\Citrix MetaFrame Presentation Server\Number of busy XML threads
\Citrix MetaFrame Presentation Server\Resolution WorkItem Queue Ready Count
\Citrix MetaFrame Presentation Server\WorkItem Queue Ready Count
\Citrix Licensing\Citrix Licensing - License Server Connection Failure
\Citrix Licensing\Citrix Licensing - Last Recorded License Check - Out Response Time
\Process(ImaSrv)\Private Bytes

    Points to check against the target server:

    • \Processor(*) produces one module per processor instance.
    • \Paging File\% Usage names a multi-instance object without an instance; the host exposes it as \Paging File(_Total)\% Usage.
    • \Memory\Pages /sec contains a space in the counter name; the Windows counter is \Memory\Pages/sec.
    • \PhysicalDisk(_Total)\% Free Space names a counter of logical disks; physical disks do not expose % Free Space.
    • The six Avg. Disk Sec/... lines contain a space between the backslash and the counter name. Remove it when the counter is not collected.
    • Every line of the shipped file ends with a space. The path is passed as read, so trim the line when the counter is not collected.
    • The Citrix MetaFrame Presentation Server and Citrix Licensing sets exist only where that Citrix component is installed.
    • Every path uses English counter names.

    Citrix Independent Management Architecture

Citrix Client Network
Citrix Streaming/Citrix Streaming Helper

Netlogon
Remote Procedure Call (RPC)

    Points to check against the target server:

    • The entries are display names. ImaSrv, for example, is the short name of Citrix Independent Management Architecture.
    • Several lines of the shipped file end with a space, and the value is used verbatim: trim the line when the service reports 0 although it runs.
    • The sixth entry ends with Estados Servicios, which is not a Windows display name pattern. It is used verbatim, so replace it with the exact display name of that service on your server.
    • Server, Workstation, Netlogon, Print Spooler and Remote Procedure Call (RPC) are operating system services. They are monitored with the same mechanism as the Citrix ones.
    • The list is a default, not a limit: any display name you add becomes a module.

    Generated modules¶

    Module name Type Value
    PerfCounter <counter path> generic_data, or generic_data_inc for the incremental set The sampled value of that counter
    Status of service <display name> generic_proc 1 when the extracted state is Running, 0 otherwise
    Citrix Sessions generic_data Number of query session lines that contain Active
    Users_Connected generic_data Number of quser lines that contain Active

    Each module is written as a <module> block with name, type, description and data elements, and no <agent> element: the modules belong to the agent that executes the plugin.

    Output and exit status¶

    Condition Behavior
    Normal run <module> blocks on standard output; the process ends with status 0
    Usage summary path The banner, the parameter list and the usage example on standard output; no modules
    Counter list unreadable or counters refused PowerShell error on standard error, no counter modules, the rest of the run continues
    Service list unreadable PowerShell error on standard error, no service modules, the rest of the run continues
    grep or gawk missing Each service reports 0; the error appears on standard error
    wc missing The run stops at the session count with You cannot call a method on a null-valued expression
    Undefined parameter The run ends before generating modules, with the PowerShell parameter error on standard error

    The script never calls exit. A run that only produces errors on standard error still finishes successfully, which is why the invocation redirects standard error to a file.
